## Зачем

Алексей: «может нам отдельный проект сделать, сайт, на который если закинуть проект, выдаёт его оценку
подробнейшую?» Повод: выяснилось, что покрытие тестами не меряется ни в одном проекте, а требования к тестам
теперь записаны в скилл project-cycle. ProjectScore показывает, насколько каждый проект им соответствует, и что
чинить первым.

## Что проверяется (разделы и вес)

1. **Тесты (35).** Число тестов и законов; прогон (зелёные/красные/пропущенные, время, медленные, мигающие при
   повторе); покрытие по ВЕТВЯМ отдельно для ядра логики (цель >= 90 %) и для кода без окон (>= 80 %); мутанты
   (свой mutate-скрипт проекта, если есть: поймано/выжило); закон многократного запуска (N >= 20, память и хэндлы);
   битые файлы настроек. Карта покрытия: файл с зелёными/красными/жёлтыми строками и выжившими мутантами.
2. **Код (20).** Сложность функций, длинные файлы и функции, дубли, мёртвый код, предупреждения линтеров
   (ruff, eslint, dotnet build warnings, luacheck); карта сложных мест плитками (размер - строки, цвет - сложность и
   покрытие); прогноз риска - файлы, которые часто меняются в git И слабо покрыты.
3. **Безопасность и личное (15).** Секреты и токены в коде и ИСТОРИИ git; личное (почта, 192.168.*, C:\Work,
   фамилия, steam id) - особенно в том, что уходит на GitHub; уязвимые и устаревшие пакеты (pip-audit, npm audit,
   dotnet list package --vulnerable).
4. **Вид (10).** Запуск без экрана (offscreen Qt, headless Chromium, WPF RenderTargetBitmap), снимки в обеих темах
   и 3 размерах; законы читаемости (шрифт >= 13 px, контраст WCAG по нарисованному, наложения, обрезанный текст,
   «В меню» видно); доступность (подписи кнопок, клавиатура, размер касаний на телефоне).
5. **Сборка и выпуск (10).** Собирается ли; версия в двух местах совпадает; тег и выпуск на GitHub; строка в
   InstallAll; CI последнего коммита зелёный; GitHub совпадает с Gitea (проверка актуальности).
6. **Оформление (5).** README EN+RU, шапка (значки отдельной строкой, «Built with Claude Code», ПУСТАЯ строка,
   строка авторства), снимки не старше версии, лицензия, CHANGELOG на каждую версию, описание и темы на Gitea и
   GitHub; свежесть документации (числа тестов и версия в README = в коде); тексты и перевод (опечатки, непереведённые
   строки, склонения «1 файлов», маленькая буква, числа с точкой в русском интерфейсе); наши правила (длинные тире,
   Ko-fi, строки авторства).
7. **Скорость и память (5).** Время запуска, память после запуска и через N минут, размер сборки, долгие кадры.
Отдельно, без баллов: **здоровье репозитория** (понятные коммиты, большие файлы в git, забытые ветки и worktree в
wip, незакоммиченное), **память проекта** (файл в памяти Claude, свежая точка продолжения, строка в каталоге и на
карте Obsidian), **требования скилла project-cycle галочками**.

## Как устроено (решения Claude)

- Сервер: Node (как Electron-проекты; запуск инструментов через child_process с тайм-аутами и пониженным приоритетом).
  Слушает только 127.0.0.1 и адрес ПК в домашней сети (для телефона), без доступа снаружи.
- Проверки - модули-«анализаторы» по языкам с общим форматом результата; каждый можно запустить из консоли
  (`projectscore <папка> --json`), агенты считают балл перед сдачей работы.
- Тяжёлое (мутанты, N запусков, снимки) - очередью, по одному, с прогрессом на странице; можно отменить.
- Чужой код (ссылка/ZIP) распаковывается во временную папку; запуск тестов из ZIP/ссылки - только после
  подтверждения кнопкой (это код Алексея, но лишний запуск не нужен).
- Данные: история в JSON-файлах в %LOCALAPPDATA%\ProjectScore (не в репо).

## Тесты самого ProjectScore

По скиллу project-cycle: законы на подсчёт баллов (баллы 0-100, вес раздела не превышает свой, нет данных - не
ноль, а «не проверено»), на каждый анализатор - маленькие проекты-образцы в tests/fixtures с известными ответами;
покрытие по ветвям: ядро >= 90 %, без окон >= 80 %; мутанты; страница - Playwright без видимого окна.
